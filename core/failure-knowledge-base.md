# 失败知识库模板（Failure Knowledge Base，FKB）

跨项目沉淀"症状 → 原因 → 验证 → 解决"的可检索知识。单条故障排查记录只对当下有用；把它结构化成一条 FKB 条目后，下一个项目遇到相似症状时，可以先按概率排序去查、而不是从头再瞎猜一遍。本模板由 `11-troubleshooting.md` 的排障环节在每次排障结束后调用，让 AI 把结论结构化沉淀下来。

定位：它不是日志、不是排障过程的流水账，而是一份"查得到、能复核、带发生次数"的经验库。每条条目都要能被未来的自己（或 AI）用一句话症状搜到，并且一眼看出"先怀疑哪个、怎么验证、怎么修"。

## 目标与通过标准

- 目标：让"同一个坑不在第二个项目里再踩一遍"。每次排障结束后，把结论从"我当时弄好了"升级为"症状 X 在 N 次复现里，60% 是原因 A，用测量 Y 可以确认，解法是 Z"。
- 通过标准：
  - 条目字段齐全：症状 / 可能原因（带概率估计） / 验证方法（可操作） / 解决 / 已发生次数 / 日期 / 相关环节。
  - 症状写得足够具体，未来用关键词能搜到（不是"板子不工作"，而是"上电后灯不亮、设备管理器无新串口"）。
  - 概率估计是"估计值 + 依据"，不是拍脑袋；没证据就写"未验证"。
  - 验证方法是可执行动作（"万用表测 3V3 对 GND"），不是"检查一下电源"。
  - "已发生次数"是真实计数，每次命中 +1；示例条目必须显式标注"示例"，不得冒充真实记录。

## 可复制操作与命令

### FKB 条目字段定义

| 字段 | 写什么 | 反面例子 |
| --- | --- | --- |
| 症状 | 具体、可观测、可搜索的现象（含环境：板子型号 / 上电状态 / 日志关键行） | "板子有问题" |
| 可能原因 | 带概率估计的原因列表；概率写"估计值 + 依据"，如"高（约 60%，曾 3 次复现）"；未验证的写"未验证" | "可能是线的问题"（无概率） |
| 验证方法 | 可立即执行的测量 / 日志 / 二分动作，写清楚"测什么、测出来说明什么" | "检查电源" |
| 解决 | 验证命中后真正生效的修复动作；没验证过的解法不要写进来 | "换个板试试" |
| 已发生次数 | 真实命中次数（整数）；新条目从 1 开始，每次复现 +1 | （编造的大数） |
| 日期 | 最近一次命中的日期（YYYY-MM-DD） | （留空） |
| 相关环节 | 对应 11 环节中的哪一层（电源 / 时钟复位 / 引脚外设 / 固件逻辑 / 协议网络） | （留空） |

### 条目 Markdown 模板（可直接复制）

```markdown
### 症状：<一句话具体症状，含板子型号与关键日志行>

- **可能原因**：
  1. <原因 A>——概率：<高/中/低 + 百分比 + 依据，如"高（约 60%，本库已命中 3 次）">；
  2. <原因 B>——概率：<中（约 25%）>；
  3. <原因 C>——概率：未验证（仅理论怀疑）。
- **验证方法**：
  1. <先做这个测量/日志，结果 X 说明原因 A 命中>；
  2. <再做这个，结果 Y 说明原因 B 命中>。
- **解决**：<验证命中后实际生效的修复动作，写具体命令/配置/接线>。
- **已发生次数**：<N>（最近一次：YYYY-MM-DD）
- **相关环节**：<电源 / 时钟复位 / 引脚外设 / 固件逻辑 / 协议网络>
```

### 条目 JSON 模板（可直接复制，适合批量检索）

```json
{
  "symptom": "<一句话具体症状>",
  "causes": [
    {"name": "<原因 A>", "probability": "high", "estimate": "约 60%，本库已命中 3 次", "verified": true},
    {"name": "<原因 B>", "probability": "medium", "estimate": "约 25%", "verified": true},
    {"name": "<原因 C>", "probability": "unknown", "estimate": "未验证", "verified": false}
  ],
  "verification": [
    "<测量/日志动作 1，及判读>",
    "<测量/日志动作 2，及判读>"
  ],
  "fix": "<实际生效的修复动作>",
  "occurrence_count": 1,
  "last_seen": "YYYY-MM-DD",
  "stage": "power | clock_reset | pin_peripheral | firmware | protocol_network"
}
```

### 存储约定

- 单项目内：把条目追加到项目根的 `docs/failure-knowledge-base.md`（Markdown 版），与 `product-contract.md` 同目录。
- 跨项目沉淀（本 skill 仓库）：维护一份 `core/failure-knowledge-base.md` 的 JSON 数组或 Markdown 条目合集，把跨项目复现 2 次以上的条目晋升进来。
- 一次排障只写一条症状；同一症状多原因在同一条目内分行，不要拆成多条重复症状。

## 可复制 AI 提示词模板

模板 A：排障后沉淀（把一次排障结论转成 FKB 条目）

```text
我刚完成一次硬件排障，过程和结论如下，请帮我把它转成一条结构化的 FKB 条目（严格按字段：症状 / 可能原因(带概率估计与依据) / 验证方法 / 解决 / 已发生次数 / 日期 / 相关环节）。要求：
1. 症状写得具体、可被未来关键词搜到；
2. 概率只写"估计值+依据"，我没验证过的原因标"未验证"；
3. 验证方法必须是可立即执行的测量/日志动作；
4. 已发生次数我明确告诉你是几就是几，不要自己编；
5. 同时输出 Markdown 版和 JSON 版各一份。
排障过程：<贴日志、测量值、试了什么、最后怎么好的>
```

模板 B：查询匹配（遇到新症状先查 FKB，按概率排序）

```text
我现在遇到这个新症状：<具体描述，含板子型号、上电状态、串口关键日志行>。
下面是我们 failure-knowledge-base.md 的全部条目：
"""
<粘贴 FKB 全文>
"""
请帮我：
1. 按相关度从高到低列出最可能匹配的 3 条条目；
2. 每条给出"它的最高概率原因 + 对应的验证方法"，让我按顺序去试；
3. 如果 FKB 里没有任何条目相关，明确说"库中无匹配"，不要硬凑。
先给排序和验证动作，不要直接改代码。
```

模板 C：概率估计校准（拿到新证据后更新概率与次数）

```text
这次排障命中了 FKB 里这条旧条目：<贴旧条目>。新证据是：<这次实测到什么 / 换了什么就好>。
请帮我：
1. 把 occurrence_count +1，更新 last_seen 日期为今天；
2. 根据新证据重新校准各原因的概率估计（哪条上升、哪条下降、依据是什么）；
3. 如果这次暴露了 FKB 里没写的新原因，补一条 cause 进去并标 verified=false；
4. 输出更新后的完整 Markdown 条目和 JSON 条目。
```

## 常见坑

1. **现象**：FKB 里堆了几十条，真遇到问题却搜不到。**原因**：症状写太笼统（"板子不工作""连不上"），没有环境和关键日志行。**解决**：症状必须含板子型号 + 上电状态 + 串口关键行（如"boot loop 无限打印 rst:0x3"），写成未来自己会搜的那句话。
2. **现象**：原因列了七八条，看起来很全，实际还是瞎猜。**原因**：原因不带概率、不带依据，变成"什么都有可能"的清单。**解决**：每条原因强制写"高/中/低 + 估计百分比 + 依据（命中几次/理论怀疑）"，没证据的标"未验证"。
3. **现象**：照 FKB 写的"验证方法"去做，还是不知道下一步干嘛。**原因**：验证方法不可操作——写"检查电源""看看接线"，而不是"万用表测 3V3 对 GND 是否 3.2~3.3V"。**解决**：验证动作必须具体到用什么工具、测哪两个点、读到什么数值算命中。
4. **现象**：三个月后同一个坑又踩一遍。**原因**："已发生次数"和概率从不更新，旧条目停留在第一次排障时的估计。**解决**：每次复现命中模板 C，把次数 +1、按新证据校准概率。
5. **现象**：AI 给的解法特别自信，结果根本没验证过。**原因**：把"理论猜测"当成"已验证结论"写进了解决字段。**解决**：`解决` 字段只写这次实测生效的动作；未验证的猜测只能放在 `causes` 里并标 `verified=false`。
6. **现象**：FKB 越写越长，全是一次性小问题。**原因**：没有"晋升"机制，只命中一次的环境杂音和跨项目通用的坑混在一起。**解决**：库内命中 ≥2 次、且与具体板子无关的条目才晋升进 core；一次性的留在项目 docs 里。

## 验收清单

- [ ] FKB 模板的七个字段在每条目里都填了，没有空字段
- [ ] 每条症状都含板子型号或关键日志行，能被关键词检索到
- [ ] 每条原因都带"概率估计 + 依据"，未验证的明确标注
- [ ] 每条验证方法都是可立即执行的测量/日志动作，写清判读标准
- [ ] "已发生次数"是真实记录，示例条目标注了"示例"
- [ ] 每次排障结束后用模板 A 跑一遍沉淀，而不是只在脑子里"记下了"
- [ ] 遇到新症状先跑模板 B 查库，再开始瞎试
- [ ] 每次复现旧条目都用模板 C 更新次数与概率
- [ ] core 库里只保留跨项目命中 ≥2 次的条目，一次性问题留在项目 docs

## 附：示例条目（从 11 环节现有故障库转化，字段演示用，非真实计数）

> 以下三条为"示例"，用于演示字段写法；其中的"已发生次数"为占位，不是真实统计。

### 示例 1：症状——上电完全没反应，灯不亮、设备管理器也没新串口（EasyInput V2.0 / ESP32-S3）

- **可能原因**：
  1. USB 线是充电线（无数据芯）——概率：高（约 50%，新手环境高频）；
  2. 只接了 5V 没接 GND / 电源开关没拨到 ON——概率：中（约 30%）；
  3. 板子本身损坏——概率：低（约 5%）。
- **验证方法**：
  1. 换一根确认能传数据的 USB 线，插主板后置口；设备管理器出现新串口即命中原因 1；
  2. 万用表测 3V3 对 GND，若 0V 则查 GND 接触与板上开关位置。
- **解决**：换数据线；量 3V3 对 GND 电压；EasyInput V2.0 开关拨到 ON。
- **已发生次数**：示例（占位，实际从 1 开始计数）
- **相关环节**：电源

### 示例 2：症状——串口 monitor 全是乱码，看不出日志（ESP32-S3 / ESP-IDF）

- **可能原因**：
  1. monitor 波特率与固件日志波特率不匹配——概率：高（约 70%，最常见）；
  2. 日志走了错误 UART 引脚——概率：低（约 15%）；
  3. 时钟配置错误导致内部波特率偏差——概率：未验证。
- **验证方法**：
  1. 两边都设 115200 重新 monitor；乱码消失即命中原因 1；
  2. `idf.py -p COM3 monitor --baud 115200` 显式指定波特率对比。
- **解决**：固件日志波特率与 monitor 波特率统一为 115200。
- **已发生次数**：示例（占位）
- **相关环节**：协议/网络

### 示例 3：症状——WiFi 一直连不上，日志反复打印连接失败（ESP32-S3）

- **可能原因**：
  1. 路由是 5GHz，ESP32-S3 只支持 2.4GHz——概率：高（约 55%）；
  2. 密码错 / 路由开了 MAC 过滤——概率：中（约 25%）；
  3. 信号弱（距离/遮挡）——概率：中（约 15%）。
- **验证方法**：
  1. 手机开 2.4GHz 热点，板子连热点能成功即命中原因 1；
  2. 核对密码字符串与路由 MAC 过滤白名单。
- **解决**：连 2.4GHz 热点；核对密码；先手机热点排除路由问题。
- **已发生次数**：示例（占位）
- **相关环节**：协议/网络
