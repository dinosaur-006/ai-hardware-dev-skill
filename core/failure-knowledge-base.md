# 失败知识库（failure-knowledge-base）

本文件是 AI 硬件开发 Skill V2 新增的"失败知识库"层（V3 升级为结构化 FKB）。定位：**把"为什么不能工作"沉淀成可检索、带概率与验证方法的故障库，让 AI 与用户不再重复踩同一个坑**。

硬件开发 80% 的时间不是设计，而是"为什么不能工作"。每次排障的结论（症状、可能原因、验证方法、最终解决）如果不沉淀，下次遇到同款问题还要从头排。

> 与其他文件的关系：排障入口在 `references/11-troubleshooting.md`（分层排查法）；本文件定义**沉淀格式**与**维护纪律**。跨项目沉淀到 `docs/failure-knowledge-base.md`；`project-memory.json` 的 `risks` 里把已缓解的风险勾掉。

## 目标与通过标准

- 目标：每个已解决的硬件问题都有一条结构化条目：症状 → 可能原因（带概率估计与依据）→ 验证方法 → 解决 → 已发生次数，可被检索、可被新症状匹配。
- 通过标准：
  - 每次排障后（无论是否解决）都在 `docs/failure-knowledge-base.md` 追加一条。
  - 每条包含七个字段：症状、可能原因（概率 + 依据）、验证方法、解决、已发生次数、日期、相关环节。
  - 概率必须是"估计值 + 依据"，**禁止编造精确统计**（如"50%"而无依据）；依据可以是"曾 N 次复现 / 目检可疑 / 手册说明"。
  - 新症状先查知识库，命中则按概率从高到低验证，而不是从零开始。

## 可复制操作与命令

本系统没有命令行，核心是维护一个 Markdown 文件（`docs/failure-knowledge-base.md`）。

### 条目 Markdown 模板（直接复制）

```markdown
## FKB-<序号>：<一句话症状，可检索>

- **症状**：<现象，如：开机 3 秒后反复重启>
- **可能原因**（估计 + 依据）：
  - <原因 A>：高（依据：曾 3 次复现 / 目检可疑 / 手册说明）
  - <原因 B>：中（依据：……）
  - <原因 C>：低（依据：……）
- **验证方法**：<可操作步骤，如：万用表测 3.3V 对 GND 应 >300Ω；monitor 看 rst 原因>
- **解决**：<最终修复方式，如：换 LDO、加去耦电容、改 BOOT 上拉>
- **已发生次数**：<数字，如 2>（示例条目请标注"示例"，不编造真实计数）
- **日期 / 环节**：<YYYY-MM-DD> / <如 06 焊接调试、08 烧录>
```

### 条目 JSON 片段（可选，供工具/脚本消费）

```json
{
  "id": "FKB-001",
  "symptom": "开机 3 秒后反复重启",
  "causes": [
    {"cause": "供电不足", "probability": "high", "basis": "曾 3 次复现"},
    {"cause": "去耦不足", "probability": "medium", "basis": "目检可疑"}
  ],
  "verification": ["万用表测 3.3V 对 GND >300Ω", "monitor 看 rst 原因"],
  "resolution": "换 LDO、加去耦电容",
  "occurrences": 2,
  "date": "2026-09-29",
  "stage": "06-soldering-and-hardware-debug"
}
```

## 可复制 AI 提示词模板

**模板 A：排障后沉淀（每次排障后必用）**

```text
刚解决了一个硬件问题，请按 core/failure-knowledge-base.md 的条目格式把它结构化沉淀：
症状：<一句话，可检索>
可能原因（带概率估计与依据）：<如：供电不足 60%（曾 3 次复现）；虚焊 30%（目检可疑）；固件 bug 10%（日志未见）>
验证方法：<可操作步骤，如：万用表测 3.3V 对 GND、示波器看波形>
解决：<最终修复方式>
已发生次数：<本次是第几次>
相关环节：<如：06 焊接调试 / 08 烧录>
请写入 docs/failure-knowledge-base.md（与 core 模板同格式），并在 project-memory.json 的 risks 里把已缓解的风险勾掉。
```

**模板 B：查询匹配（新症状先查知识库）**

```text
我的板子现在出现：<症状描述>。请先查我的失败知识库 docs/failure-knowledge-base.md（若为空则用 references/11-troubleshooting.md 的种子故障库），按"可能原因概率从高到低"列出匹配条目与对应验证方法，再开始排查；不要从零列假设。
```

**模板 C：概率校准（新证据后更新）**

```text
失败知识库条目 <FKB-序号> 的概率估计是 <旧概率+依据>，现在有了新证据：<新现象/新复现次数/新解决方式>。请按新证据更新：① 各原因概率估计与依据；② 已发生次数；③ 验证方法是否有更快的捷径。更新后给出一句话结论。
```

## 常见坑

1. **现象**：概率写成"50%""55%"这种精确数字，却没有任何统计来源。**原因**：把"估计"伪装成"统计"。**解决**：用"高/中/低 + 依据"；依据写"曾 N 次复现 / 目检可疑 / 手册说明"，不编造精确百分比。
2. **现象**：排障结束不沉淀，下次遇到又从头查。**原因**：没有沉淀纪律。**解决**：模板 A 是每次排障后必用。
3. **现象**：条目只写症状和解决，没写"怎么验证"。**原因**：跳过了诊断过程。**解决**：验证方法是必填字段——它让下一个人能复现你的排查路径。
4. **现象**：新症状不查知识库，直接列 10 条假设。**原因**：没有检索习惯。**解决**：模板 B 强制先查库再排。
5. **现象**：已发生次数被编造（"第 5 次"其实第 2 次）。**原因**：为显得专业而编数字。**解决**：如实写；不确定就写"≥2"或"示例"。
