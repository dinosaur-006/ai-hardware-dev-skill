# 11. 故障排查（Troubleshooting）

全流程的"安全网"。前面任何环节（硬件焊接 / 固件逻辑 / 软硬件联调）出现"不亮 / 不响 / 连不上 / 一直重启"时，回到本环节用分层法定位。输入：一个具体症状 + 串口日志；输出：定位结论 + 修复 + 一条沉淀进故障库的"现象→原因→解决"。

## 目标与通过标准

- 目标：建立"分层排查 + 日志驱动 + 证据纪律"的排障习惯，而不是瞎猜瞎换。
- 通过标准：
  - 遇到问题能按"电源→时钟/复位→引脚/外设→固件逻辑→协议/网络"逐层排查，知道每层用什么手段。
  - 能看懂串口日志的关键行：`rst:0x...` 复位原因、`Guru Meditation Error`、`Backtrace`。
  - 能区分"编译通过 / 烧录成功 / 日志正常 / 真机表现对"四件事，不互相冒充。
  - 每次排障结论沉淀成一条"现象→原因→解决"。

## 可复制操作与命令

### 分层排查法（从硬到软，逐层排除）

| 层 | 怀疑什么 | 怎么查 |
| --- | --- | --- |
| 1 电源 | 没供电 / 电压不对 / USB 线只充电不传数据 | 万用表测 3V3-GND；换一根数据线；看设备管理器有没有新串口 |
| 2 时钟/复位 | BOOT 状态错、boot loop、brownout | 上电第一行日志的 `rst:0x...` / `boot:0x...`；EN 引脚 |
| 3 引脚/外设 | 接错脚、电平不匹配、虚焊 | 万用表测 GPIO 静态电平；对照板子丝印；换个脚试 |
| 4 固件逻辑 | 空指针、栈溢出、死循环、看门狗 | IDF Monitor 看 Guru Meditation / backtrace；二分注释代码 |
| 5 协议/网络 | 串口乱码、WiFi 2.4G/BLE 连不上 | 核对波特率；连手机热点排除路由；看串口有没有数据 |

### 第一步永远是：插串口看日志

PowerShell（ESP-IDF 终端环境里）：

```powershell
idf.py -p COM3 monitor
```

macOS/Linux：

```bash
idf.py -p /dev/ttyUSB0 monitor
```

上电瞬间前几行最关键：

```text
rst:0x1 (POWERON_RESET),boot:0x8 (SPI_FAST_FLASH_BOOT)
...
cpu_start: ESP-IDF v5.x
```

- `rst:0x...` 是复位原因；`Guru Meditation Error` 后面括号里是异常类型；`Backtrace:` 下一行 `app_main at xxx.c:行号` 通常就是元凶。
- 看到崩溃后无限重启，先在 menuconfig 里把 panic 行为改成"打印后暂停"，让日志停下来。

### 二分法定位固件问题

怀疑某段代码导致崩溃/卡死时：

1. 把 `app_main` 后半段注释掉，只留点灯 + 串口打印，烧录看是否正常。
2. 一半一半地恢复代码，直到崩——bug 就在刚恢复的那一半里。

PowerShell 里快速看最近改了什么：

```powershell
git diff --stat
git log --oneline -5
git diff HEAD~1
```

macOS/Linux 相同。**新现象先怀疑自己最近的改动**：上一个 commit 能不能跑？能就是这次引入的。

### 日志级别与关键点打印

```powershell
idf.py menuconfig
# Component config -> Log output -> Default log verbosity -> Debug
```

关键路径加打印（ESP-IDF 自带时间戳）：

```c
ESP_LOGI(TAG, "btn pressed i=%d v=%d", i, v);
ESP_LOGW(TAG, "wifi retry %d", retry_count);
ESP_LOGE(TAG, "i2s write failed: %d", err);
```

怀疑两个模块之间卡住时，在中间插 `ESP_LOGI(TAG, "reach A")` / `"reach B"`，看日志停在哪一行。

### 把日志喂给 AI

不要只截图。复制**从上电到复现问题之间的完整文本日志**，连同下面"模板 A"一起贴给 AI；只贴最后一行它无从下手。

### 串口乱码时先核对波特率与串口号

```powershell
Get-PnpDevice -Class Ports | Where-Object {$_.Status -eq 'OK'} | Select-Object FriendlyName
```

板子默认日志 115200；板子改了波特率而 monitor 没改，就是乱码。

模板 C：硬件 vs 软件二分（不知道是哪边的问题）

```text
我的设备出现：<如：WS2812 不亮 / I2S 无声 / 按键按了没反应>。我不确定是硬件接线问题还是固件代码问题。请给我一个"二分法"排查方案：
1. 怎么用最小固件（不依赖我的业务逻辑）单独验证硬件本身好坏；
2. 怎么用 PC 端 mock 数据 / 串口手动发命令单独验证固件逻辑；
3. 两个测试分别过了/没过的四种组合，各自说明问题在哪、下一步做什么。
```

模板 D：安全类故障排查（喂 WDT / 过流 / ESD / 电池）

```text

- 串口日志关键行：<贴 rst 原因、WDT 报错、brownout 提示等>

- 电池情况：<是否带保护板、最近一次充电多久前、有没有鼓包/发烫>
请你按"安全优先"的顺序带我排查：
1. 先判断是否属于过流/短路/电池热失控类风险，若有，立刻告诉我该断电还是该隔离；
2. 再分别给出对应排查路径：看门狗循环复位（喂狗位置/WDT 超时/AI 长阻塞）、保险/PTC 过流断开（先找短路源再换件）、ESD 损 GPIO（换脚验证）、锂电池保护板锁定（量电芯 vs 输出、按规格书激活）；
3. 每一步写清"测什么、用哪一档、正常读数是多少、超过多少必须停手"。
不要让我在没排除短路前就直接换保险或短接保护点。
```

## 常见坑（结构化故障库 v1）

> 字段说明：每条"症状"可能对应多个"可能原因"，按可能性从高到低分行排列。可能性写法为"高/中/低 + 判据"（判据=这条怀疑为什么排前面，如"换线即好""目检可疑"），**没有真实统计来源时不写百分比数字**——编造的百分比会误导后续排查；未验证的纯理论怀疑写"未验证"。**已发生次数**是真实复现计数，本表为种子条目，初始统一记为"待累计"，由你在自己项目里命中后逐次 +1（维护方法见下节"排障后沉淀"）。

| # | 症状 | 可能原因（可能性与判据） | 验证方法 | 解决 | 已发生次数 |
| --- | --- | --- | --- | --- | --- |
| 1 | 上电完全没反应，灯不亮、设备管理器也没新串口 | USB 线是充电线（无数据芯）——高（新手最高频，换线即好） | 换一根确定能传数据的 USB 线，插主板后置口；设备管理器出现新串口即命中 | 换数据线 | 待累计 |
| 1 | 同上 | 只接了 5V 没接 GND / 板上电源开关没拨到 ON——中（供电链路上最常见的次因） | 万用表测 3V3 对 GND；若 0V 查 GND 接触与开关位置 | 量 3V3 对 GND；按板级合同/丝印确认电源开关位置 | 待累计 |
| 2 | USB 插电脑出现未知设备 / 黄色感叹号，或串口时有时无 | 外挂串口芯片（CH340/CP210x）驱动没装——高（设备管理器直接可见） | 设备管理器看硬件 ID，对照芯片型号 | 在设备管理器看硬件 ID 装对应驱动 | 待累计 |
| 2 | 同上 | 前置 USB 口供电不稳——中（换后置口可对比验证） | 换主板后置口对比 | 换主板后置 USB 口 | 待累计 |
| 3 | `idf.py flash` 一直失败，报 "Failed to connect to ESP32-S3" | 没进下载模式——高（烧录失败第一因，按板级合同进下载模式即命中） | 按 `<board-contract:boot.enter>` 让板子进入下载模式（具体进/退动作与是否需重上电以 `docs/board-contract.json` 的 `boot.enter`/`boot.exit` 为准） | 按板级合同进下载模式 | 待累计 |
| 3 | 同上 | 串口被其他程序占用——中（关掉再试即可验证） | 关掉 IDF Monitor / Serial Studio / 串口助手再试 | 关掉占串口的程序 | 待累计 |
| 3 | 同上 | 烧录波特率太高——低（少见，需降速才复现） | 降低烧录波特率重试 | 降低烧录波特率 | 待累计 |
| 4 | GPIO 量出来一直是 0V 或 3.3V 不动 | 脚没配成输出——高（最小例程一测即知） | 最小例程 `gpio_set_direction` + `gpio_set_level` 翻转，万用表应跟随变化 | 先最小例程验证，再回到业务代码 | 待累计 |
| 4 | 同上 | 被其他外设占用——中（查引脚表可发现冲突） | 对照板级合同引脚表查是否被 SPI/I2S 等占用 | 换个脚试 | 待累计 |
| 4 | 同上 | 量错脚——中（目检丝印容易看错） | 对照板子丝印和板级合同引脚表重新确认测试点 | 对照丝印重新量 | 待累计 |
| 5 | 按键按下去串口完全没事件 | 没开内部上拉/下拉——高（电平不跳即命中） | 万用表量按下/松开时引脚电平是否在 0/3.3V 间跳 | `gpio_pullup_en` 内部上拉 | 待累计 |
| 5 | 同上 | 消抖缺失——中（注意：这通常表现为偶发误触发，而非完全无事件；完全无事件先怀疑上拉） | 按住不动看串口是否稳定打印一次 | 代码加 20ms 消抖 | 待累计 |

| 7 | 同上 | 采样率不匹配——中（换采样率可对比） | 采样率用 16000 / 44100 分别试 | 调整采样率 | 待累计 |
| 7 | 同上 | 音量为 0 / DMA buffer 太小——中（官方例程可隔离） | 先烧官方 i2s 例程确认硬件 | 官方例程确认硬件后再调音量与 buffer | 待累计 |

| 8 | 同上 | L/R 使能脚拉错——中（量使能脚电平可判） | 万用表量使能脚电平 | 正确设置使能脚电平 | 待累计 |
| 8 | 同上 | 时钟没出来——中（量 SCK 有无跳变可判） | 量 SCK 引脚有没有跳变 | 查 I2S 时钟配置 | 待累计 |

| 10 | BLE 手机扫不到 / 连不上 | 广播没开——高（代码里查调用即可） | 代码确认调用了 `esp_ble_gap_start_advertising` | 开广播 | 待累计 |
| 10 | 同上 | 手机蓝牙缓存——中（重启蓝牙可验证） | 重启手机蓝牙；在系统蓝牙里"忽略此设备"再重连 | 重启蓝牙 / 忽略设备后重连 | 待累计 |

| 16 | 断电后重新上电完全不工作，测电源入口开路 | 某路负载短路/过流，触发保险丝熔断或 PTC 自恢复断开——高（量入口开路即命中） | 断电后用通断档量保险丝/磁珠两端是否通；PTC 常温应导通、动作后开路、冷却后自恢复 | 沿电源轨分段用蜂鸣档找短路源；根因排除前不要直接换保险/短接 PTC | 待累计 |
| 16 | 同上 | 上电冲击过大把慢断保险冲断——低（无明显短路、多次上电后才断时怀疑） | 限流上电时看冲击电流；核对保险额定值裕量是否不足 | 换额定合适的慢断保险；坚持先限流再全压 | 待累计 |
| 17 | 某个对外 GPIO 功能时好时坏，或永久失效，与其他脚表现不一致 | 对外接口没加 TVS/ESD 保护，触摸时人体静电打坏 IO——中（干燥季节/冬天高发，多在触摸板后才坏） | 把同功能换到另一个 GPIO 试；坏脚量对 GND 是否异常低阻/漏电；与好脚对照 | 对外信号口加 TVS/RC 吸收；下次触摸前先摸接地金属放电、戴手环 | 待累计 |
| 17 | 同上 | 该脚已被过压或烙铁漏电等物理损伤打死——低（换脚后硬件即恢复可坐实） | 换脚后功能恢复即原脚已损 | 坏脚报废不用；必要时返修/换板 | 待累计 |
| 18 | 插充电器无反应、电池端量到 0V 或远低于标称电压 | 过放触发保护板过放保护、锁死切断输出——高（量电池芯电压与保护板输出对比可判） | 万用表量电池芯两端 vs 保护板输出端；芯有电但输出 0V = 保护板锁 | 按该电池规格书的激活流程激活（以规格书为准），激活不了更换电池；以后低电及时充 | 待累计 |
| 18 | 同上 | 近期短路/反接触发保护板过流保护后锁死——中（回顾是否短路过） | 解除全部负载后重新插充电头看是否恢复；回顾近期有无短路/反接 | 解除短路根因后再充电唤醒；反复锁死则换保护板/电池 | 待累计 |

### brownout 反复重启专项（AI 负载大电流是头号嫌疑）

"开机后反复重启 / 一跑 AI 或一连 WiFi 就复位"，先怀疑供电被瞬间大电流拉低触发 brownout 复位，而不是先怀疑代码：

- **大电流来源**：WiFi TX 峰值可达 400mA+；NPU/加速器做一次推理 burst 电流；板载 LDO 瞬态响应跟不上这种突变。三者叠加把 3.3V 轨瞬时拉低 → 芯片欠压复位（brownout reset）。
- **验证方法**：
  1. 看串口上电日志里的 `rst:0x...` / brownout 提示（brownout 复位会明确打印 brownout 相关行）；
  2. 用万用表/示波器测 3.3V 轨在"开 WiFi TX"或"跑一次 AI 推理"瞬间的跌落——若掉到芯片最低工作电压以下即命中。
- **缓解（按代价从小到大）**：在 3.3V 对地加大旁路/储能电容；换瞬态响应更好、dropout 更低的 LDO；用 `esp_wifi_set_max_tx_power()` 降低 WiFi TX 功率；最后才是把大电流任务错峰、降频。

### JTAG / 内置 USB-Serial-JTAG 排障入口

ESP32-S3 原生 USB 内置 **USB-Serial/JTAG**，**无需外接调试器**。板子插上后，设备管理器除 COM 口外还枚举到一个 "USB JTAG/serial debug unit"（对应板级合同 `usb` 段）时即可使用：

- **可稳定复现的崩溃**：用 JTAG 挂断点、单步、读异常地址（exception cause / epc）与调用栈，比纯串口日志更快定位空指针/栈溢出。
- **串口抓不到的早期 panic**（boot 阶段就挂、来不及打日志）：JTAG 能在崩溃瞬间停住，直接看寄存器与 backtrace。
- 排障完断开 JTAG 会话即可，不影响正常串口 monitor。
- 完整调试教程（断点/单步/变量查看/OpenOCD 流程）见环节 08「### 9. JTAG 调试」，本节只给排障入口。

## 排障后沉淀（Failure Knowledge Base）

上面这张表是"种子故障库"，不是终点。每一次你真实排障结束后，都要把结论沉淀成一条结构化 FKB 条目，追加进项目内 `docs/failure-knowledge-base.md`（模板见 `core/failure-knowledge-base.md`），字段为：

- **症状**：具体、可检索（含板子型号 + 关键日志行）
- **可能原因**：带可能性估计（"高/中/低 + 判据"；**无真实统计来源时不写百分比数字**，编造数字会误导；未验证写"未验证"）
- **验证方法**：可立即执行的测量/日志动作，写清判读
- **解决**：实测生效的修复
- **已发生次数**：真实计数，本次命中 +1
- **日期**：最近一次命中（YYYY-MM-DD）
- **相关环节**：电源 / 时钟复位 / 引脚外设 / 固件逻辑 / 协议网络

维护纪律：

1. **排障完当场沉淀**：不要"下次再写"。排障结束后立刻用 `core/failure-knowledge-base.md` 里的"模板 A（排障后沉淀）"把结论转成条目，贴给 AI 输出 Markdown + JSON 双版本。
2. **遇到新症状先查库**：用"模板 B（查询匹配）"把 FKB 全文喂给 AI，按概率排序先试最高概率原因的验证方法，而不是从第一层重新瞎猜。
3. **复现旧条目就校准**：命中已有条目时，用"模板 C（概率校准）"把次数 +1、按新证据重新估计概率——避免上面这张种子表停留在"第一次排障时的猜测"。
4. **不编造次数**："已发生次数"必须是你真实复现的次数；不确定就写"待累计"或 1。种子表里的可能性排序是经验判据，不是你的项目统计；命中后用模板 C 校准，不要保留任何编造的百分比数字。
5. **区分"猜测"与"已验证"**：只有这次实测生效的动作才能写进"解决"；没验证过的怀疑放在"可能原因"里并标"未验证"。
6. **跨项目晋升**：同一条目在 ≥2 个项目里命中过，再把它晋升进 `core/failure-knowledge-base.md`；一次性、环境相关的问题留在项目 docs 里即可。
