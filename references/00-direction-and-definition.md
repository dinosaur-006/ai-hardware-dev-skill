# 00. 方向确定与产品定义（Direction & Product Definition）

全流程的第 1 步。在动手画板、写代码、买元器件之前，用一张纸（一个 `product-contract.md`）定义清楚"做什么、给谁用、核心交互、验收标准"，让后续所有环节都有据可依。输入：你的兴趣与训练营所学；输出：一份可执行的 MVP 产品合同。

## 目标与通过标准

- 目标：把"我想做一个 AI 硬件"这种模糊想法，收敛成"2 周内能做出最小可用版本（MVP）"的具体产品定义。
- 通过标准：
  - 能用一句话说清产品是什么（"一个能……的……"）。
  - 目标用户与使用场景明确（谁、什么时候、在哪用）。
  - 核心功能 3-5 条；**非目标（明确不做的事）**也写清楚——对零基础者，砍掉功能是最省钱的决策。
  - 验收标准可检验，全部以"能/可"开头（不是"好用"，而是"能开机自报电量"）。
  - 已决定只做最小版本，并写出第二版要补什么。
  - **MVP 必须先在一块现成开发板（如参考案例板）上跑通，再决定是否自画板**（评审要求；先 03a 面包板原型验证，跑通后再进 03b/04，不要一上来就画自己的 PCB）。

## 可复制操作与命令

本环节是纯文本工作，没有命令行。操作步骤：

1. 回答"产品定义四问"，把答案写进 `docs/product-contract.md`：

| 问题 | 要写清楚什么 | 反面例子 |
| --- | --- | --- |
| 一句话描述 | 谁 + 做什么 + 核心价值 | "一个智能盒子" |
| 目标用户与场景 | 具体的人、具体时刻、具体地点 | "所有人" |
| 核心功能（3-5 条） | 每条以动词开头、可演示 | "很智能" |
| 非目标 | 明确不做的功能/场景 | （不写） |

2. 用下面"可复制 AI 提示词模板"里的模板 A/B/C 生成并收敛合同。
3. 把合同放进项目文件夹的 `docs/` 下，后续每个环节开始前先重读它。

建议的项目文件夹结构（现在创建，后面环节逐步填充）：

```text
my-ai-device/
├── docs/
│   ├── product-contract.md   # 本环节产物：一句话/场景/功能/非目标/验收
│   └── (后续：选型、原理图、排障等记录)
├── hardware/                 # 原理图与 PCB 工程（第 03/04 环节）
├── firmware/                 # 固件工程（第 07 环节）
└── scripts/                  # 自己写的辅助脚本
```

## 可复制 AI 提示词模板

模板 A：评估产品想法（先用这个）

```text
我是一个零基础、用 AI 辅助开发（vibecoding）的硬件新手，只有一块 <开发板名>（<板子规格>）。请帮我评估下面这个产品想法，并从"开发难度、元器件成本、能否用 MCU 实现、最快可验证的最小版本"四个维度给出建议和改造方案：
产品想法：<一句话描述>
目标用户：<谁>
核心功能：<3-5 条>
```

模板 B：生成产品合同（用模板 A 的结果喂给它）

```text
请根据以下信息，帮我生成一份 docs/product-contract.md（中文，用表格），包含：一句话产品描述、目标用户与使用场景、核心功能清单（动词开头）、明确不做的事（非目标）、可检验的验收标准（每条以"能/可"开头）。信息如下：
<粘贴模板 A 的输出>
```

模板 C：砍 MVP 边界（防止范围失控）

```text
这是我要做的产品：<一句话描述>。请帮我把第一版（MVP）范围砍到最小：只保留哪些功能、砍掉哪些、为什么砍；再给出第二版补什么。我是一个人、零基础、预算有限、希望 <两周> 内做出能 <点亮/发声/对话> 的版本。
```

## 常见坑

1. **现象**：一上来选"酷但难"的方向（如 Jetson 视觉机器人、多模态大模型设备）。**原因**：被前沿 demo 吸引，忽略成本与周期。**解决**：第一个项目控制在"2 周内能点亮、发声或对话"的规模，选型见 `01-platform-selection.md`。
2. **现象**：没有验收标准，永远在"再加一个功能"。**原因**：把"做完"理解成"做完所有功能"。**解决**：先写"能/可"式验收清单再开工，验收过就冻结功能。
3. **现象**：功能越加越多，范围失控。**原因**：没有书面的非目标清单。**解决**：用模板 C 强制砍到 MVP，把砍掉的写进"第二版"。
4. **现象**：只靠脑子记需求，一周后连自己都忘了当初要什么。**原因**：没有落盘。**解决**：建 `docs/product-contract.md`，每个环节开始前重读。
5. **现象**：复刻别人的成品却看不懂代码，出问题无法排查。**原因**：纯复制粘贴。**解决**：复刻项目时让 AI 逐段讲解、自己重写关键逻辑，见 `07-firmware-ai.md`。
6. **现象**：忽视交互边界（语音助手没网了怎么办、按键按下去没响应怎么提示）。**原因**：只定义"正常路径"。**解决**：合同里加一条"离线/失败/误操作时的表现"。

## 验收清单

- [ ] 一句话产品描述已写入 `docs/product-contract.md`
- [ ] 目标用户与使用场景已明确（谁、何时、何地）
- [ ] 核心功能 3-5 条已列出（动词开头）
- [ ] 非目标（明确不做的事）已列出
- [ ] 验收标准全部以"能/可"开头且可检验
- [ ] MVP 已砍到最小，并写明第二版补什么
- [ ] 已明确：MVP 先在现成开发板（如参考案例板）上跑通，再决定是否自画板（先 03a 原型、后 03b/04）
- [ ] 项目在 2 周内可完成规模内（点亮/发声/对话级别）
- [ ] 已确定本产品用哪块板（见 01 环节）
